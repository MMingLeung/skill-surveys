## 2. 它是什么

这是一套可安装的规格驱动流程。一条安装命令把发现、需求、设计、任务和实现放进编码代理。发现阶段先把新工作分成五条路：扩已有规格、不写规格直接改、新建一份规格、拆成多份，或混合。需求用 EARS 式的验收句，设计里有文件结构计划，任务带边界和依赖。人在阶段门上看契约，代码仍是最终事实。

规格在这里是部件之间的合同，不是交给代理的总提示。作者写明：一个人一轮就能做完的改动、一次性原型，以及把边界写下来比动手更贵的时候，不必用这套。发现阶段的「不写规格」覆盖缺陷修复、配置、简单重构和很小的追加。

README 写明 Claude Code 和 Codex 的技能安装是稳定的，Cursor 标成 beta。装上 17 个技能，不等于这个宿主跑得通完整的自主循环；没有原生子代理时，实现和复查改在同一上下文里做。

## 3. 写法特点

- 每个技能的 description 只做一件事。发现技能是入口：先扫规格元数据（名字、阶段、是否已批准），不读全文；只有需要新规格的路径才加载深上下文。子代理交回的摘要有行数上限。澄清问题一次问一个，先问边界和明确不归这份规格管的部分，再问功能细节。路径定了就建议下一条命令并停。
- 边界这个词跨阶段保持同一条链：发现时的候选边界，需求里的纳入和排除，设计里的边界承诺，任务上的边界标记，集成验证时的越界。需求草稿在复查门通过之前不写入正式文件。EARS 句式和复查标准放在技能旁边的规则文件，不写进入口。
- 实现技能先看任务是否已批准，未批准就停。验证命令从仓库自己的清单、任务运行器和 CI 里找，不现编一条。一次迭代只做一个子任务。复查默认开着；说法含糊时保持开着，只有明确说跳过才关上。
- `kiro-verify-completion` 用在声称完成、声称修复、声称测试通过或报功能通过之前。结果是已核实、未核实，或必须人工核实。证据必须来自当前代码。说法不能宽过证据。测试全过仍不够报功能通过，还要有运行起来的冒烟、需求覆盖、跨任务衔接和设计对齐。技能里有一张常见借口表：子代理说成功了、早先测试过了、检查代码风格等于构建成功、任务打了勾等于功能完成。
- `kiro-validate-impl` 只看任务合在一起之后的缝，并写明自己不重查每一条任务级验收。结论是通过、不通过，或必须人工核实。
- 调试技能在实现卡住或复查两轮仍不收敛时才进入，先写根因和类别，再写修复计划和下一句动作，并限制轮数。

## 4. 原理与设计意图

代理写得快，跨模块一起改时，没写下来的接口会静默坏掉。规格被收成够小的一块，是为了让人和代理可以并行，又不用把所有决定收成一份总计划。人审的是边界和依赖是否诚实，实现落在边界里面。

完成被单独做成一道门，是因为勾选、早先的测试输出和子代理的成功报告都会和当前代码脱节。发现阶段保留「不写规格」，是为了不让这套流程包住每一行小改。宿主做不到独立复查时改成同上下文复查，是为了不把「装了技能」说成「已经有了第二双眼睛」。

## 5. 对照本库

本库一次 DEMO 用 `demo-kickoff-card` 进场，用 `dev-review-verify` 收工，跨天的行为变化用 `dev-process-handoff` 留下。

### 可借鉴

- `demo-kickoff-card` 仍是一页四块。很小的改动不另起需求、设计和任务三份文件。发现阶段允许「直接改」，和本库不为简单问答另开流程是同一方向。
- `dev-review-verify` 在写下验收完成之前，证据来自这一次，并且和这句话一样宽。检查脚本的退出、旧的测试日志，都不证明窗口或导出文件已经可用。必需的检查跑不了，结论是未验收完成。
- `dev-process-handoff` 继续写行为、默认值和验收变化。不改用他们的边界标记语法。
- `drission-crawler` 继续一次只改一个原因，再用当次回读。这和「一次迭代只做一个子任务、证据对准任务边界」同向。

### 不要照搬

- 不安装 cc-sdd，也不把这 17 个技能放进本库。
- 不要求 DEMO 之前先有 EARS 需求、设计稿和任务清单。
- 不增加实现、独立复查、自动调试三个角色，也不按任务自动提交。
- 不把 Cursor 的 beta 安装当成这些交付技能的运行方式。装上技能不等于宿主真能拦住错误的完成声明。

## 6. 一句话建议

新工作先判断要不要写规格；声称完成之前，要用当次、且和说法一样宽的证据。本库继续用开工卡和 LIVE，不铺一套规格树。
