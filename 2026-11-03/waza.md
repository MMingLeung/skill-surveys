- 星标：7502（当日 GitHub API `stargazers_count`）

- 八个技能在 `skills/<名>/SKILL.md`：`think`、`ui`、`check`、`hunt`、`write`、`read`、`learn`、`health`。`plugins/waza/skills/` 是同一套的插件副本。给人看的路由索引是 `skills/RESOLVER.md`，校验脚本也读它。仓库没有 `evals/` 目录。`scripts/verify_skills.py` 检查的是 frontmatter、结果约定、路由和分发是否还对得上，不检查一次真实任务有没有做对。

## 2. 它是什么

Waza 把作者自己的工程习惯收成可安装技能。每个技能只管一个阶段，做完就停。串联要使用人明确授权下一步：想方案用 `think`，界面用 `ui`，合并或发布前用 `check`，已经坏了的行为用 `hunt`，改文案用 `write`，陌生领域收成文章用 `learn`，读链接或 PDF 用 `read`，代理配置和指令漂移用 `health`。

它不是产品 SDK。README 写明相对更重的技能套件，这里只留八个，触发条件分开。可选的长期规则（英文纠错、行为防错、技能路由、清晰表达）默认不随安装打开。

## 3. 写法特点

- 每份 description 在「何时用」后面写 `Not for`。`think` 不修缺陷、不改小文件；`check` 不追根因、不改文章；`hunt` 不做代码审查、不做新功能；`health` 不修应用缺陷、不审 PR；`write` 不改代码注释和提交说明；`read` 不读仓库里已有的本地文本；`learn` 不做一次就能查完的问题；`ui` 不做后端和数据管道。
- `RESOLVER.md` 是歧义表，并写明改 description 时要同步改这里。两条都可能命中时，更具体的优先：设计登录页走 `ui`；先把链接取回来再决定要不要研究；已经交付的 diff 走 `check`，跑起来错了走 `hunt`；代理自己不听话走 `health`；要写发布说明走 `write`，要打标签和推送走 `check`；截图说难看走 `ui`，截图证明以前是好的走 `hunt`。还模糊，就读两边的 `Not for`，再问人。两个都可能相关时，两份都读。
- 入口用一份结果约定：要得到什么、怎样算做完、证据是什么、交什么。`check` 另写授权：只读的请求可以看工作区和远端状态，改文件、提交、推送、发布、评论和关闭都要当前请求里的授权，或者仍对同一件未完成任务有效的授权。看过草稿不等于可以提交。
- 模式选择只点到旁边的 reference，入口不把每种模式写全。持久上下文若存在，当前仓库、diff 和 CI 盖过记忆。私人记忆不能被引用成项目的公开要求。把一次经验收成持久规则之前要过打码。
- `think` 在使用人批准前不写代码。批准过的计划里不留待定。带报错的「判断一下」先改走 `hunt`。计划若增加使用人没要的层，要先说出更笨但更短的做法，并说明复杂做法赢在风险、回滚或延迟上的哪一点。
- `check` 的审查、分诊和发布判断默认只出报告。验证句必须来自这一次会话。多条目的请求用编号收尾：做了、不适用、还剩什么。动手前先看工作区状态。
- 项目约束从目标仓库公开的 README、清单、Makefile 和 CI 里现读。技能正文不写证书路径、令牌和私人机器路径。判断留在技能里；同入同出的校验留在脚本里。索引写明不要把 lint 写成技能。

## 4. 原理与设计意图

没有阶段边界时，模型会在同一轮里又计划、又改、又审、又发布，也会把否决过的方案从头再来。八个 description 都会被「帮我看看」叫到，所以把不负责什么写进会被检索的那一句，并用一张表处理剩下的重叠。

授权按动作分开，是因为同意审查不等于同意推送。习惯保持通用，项目自己的发布清单留在那个仓库里现读，技能才不会变成某一个产品的检查表。可选规则默认关闭，是为了安装技能不等于改掉使用人的全局指令。

## 5. 对照本库

本库八个技能已经按交付阶段分开。Waza 对得上的是「入口写清不负责什么」和「证据来自这一次」。

### 可借鉴

- `drission-crawler` 的 description 继续写清能直接请求就不开浏览器，登录、验证码和提交交给使用人。
- `work-doc-writer` 在文种判断旁边保持不负责哪一种。`government-service-design` 继续管政务界面的尺寸和配色，不改去套一套个人界面口味。
- `dev-review-verify` 的验证句来自这一次。多页 DEMO 里一条必需路径失败，整次不算通过。只读的审查不顺便改文件。
- `dev-process-handoff` 写下一步的一句动作，以及这次否决过的路径。当前代码和当次页面盖过旧笔记。
- `demo-kickoff-card` 的四块已经放下目标、不做的范围、做法和怎么验收。一次 DEMO 不另写一份长计划。
- `windows-gui-bat-launcher` 的就绪仍看窗口和标志文件，不凭「脚本应该已经起来了」收工。

### 不要照搬

- 不安装这八个技能，也不把他们的输出首行标记写进本库。
- 不新增一份总路由文件。分流继续写在各技能的 description 里。
- 不复制状态栏、可选全局规则，或从会话里沉淀私人习惯的脚本。
- 不把发布、推送、关闭议题做成技能。本库的交付不走那条路。
- 不让 `write` 替换 `work-doc-writer` 的模板，也不让 `ui` 替换政务界面规范。

## 6. 一句话建议

每个技能在 description 里写清不负责什么，证据必须来自当次；本库把这句写进已有入口，不另装一套个人习惯技能。
