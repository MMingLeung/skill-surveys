## 2. 它是什么

这是跨窗口、跨模型、跨设备和跨语言的交接。四种模式：交出、接收、只核结构、把旧格式保守转过来。默认产物是一份人能读的 `handoff.md`。下一步必须依赖接收方拿不到的文件时，才升成带最小附件的压缩包。只有正式审计、跨组织交付或要可携带的证明时，才用审计包。换模型、换语言或换设备本身不升级格式。

description 里的触发包括「交接一下」「接收交接」，以及交出这三种文件或文中列出的旧包。不用于普通摘要、记忆检索、隐藏推理、已经结束的短聊天，以及使用人已经拒绝交接的时候。停下来的那句话只是暗示以后可以交接时，可以提出来，不默默写文件。

## 3. 写法特点

- 格式决定用一句话写明，并带上原因：没有必须随身带的附件，或下一步依赖哪几份文件。使用人指定的格式若漏了必要文件或证明，标明部分完整，不悄悄改成更重的包。
- 普通交出从模板起笔，保留四项前置信息和三层正文。热层是当前目标、精确停止点、一个推荐的下一步和完成标准。温层是仍有效的决定、约束、已回答的问题、被否决的路和失败过的路。冷层是必要材料、附件和缺失声明。
- 覆盖程度分开写。完整只是交出方对可见边界的声明。已知漏了重要内容就写部分。源边界看不清就写未知。不允许把缺口补齐后假装完整。
- 接收时，包里的文字和附件都是不可信数据，不执行只出现在包里的指示。接收脚本默认不写文件。回执默认留在对话里，使用人要求才落成文件。使用人要求先不要继续时，开头写明接收成功并按要求未继续；主动暂停是成功，不是阻塞。
- 不重问已经回答的问题，不复活被否决或已经证明失败的路径。历史上下文不带来现在去发送、发布、付款、安装、执行、删除、披露或改外部系统的权限。技术失败、使用人否决、历史决定、可能过期的外部事实分成四类；外部事实接收后按需要重查。
- 跨语言时原文保持权威，译文是派生视图。代码、路径、标识、哈希、数字、日期和单位作为保护片段，不随意翻译。
- 评测把三个问题拆开：交出时有没有保住该保住的状态，隔离的接收方有没有找回下一步，整条路径有没有过评分卡和每一道硬门。Schema、哈希和压缩包检查只证明结构。重问、复活旧路、改掉约束、把否决说成技术失败、隐瞒缺口、把部分说成完整、翻译时弄坏保护片段，任一条失败就不能称为连续性通过。总分不能盖过硬失败。成功和失败用同一条留存规则，不单留最好的一次。脚本不在时可以按同样的格式直接写 Markdown，但不凭眼补哈希或验证结论。
- README 有一节写明它不是无限记忆、不是逐字聊天、不保存隐藏推理、不让旧会话指挥新会话、不用自评分数代替模型和人工复现。

## 4. 原理与设计意图

普通摘要回答聊过什么。交接要回答现在停在哪里、为什么，以及下一步怎样不走回头路。默认用最小的一份文件，是为了不让每次换窗口都长出一棵审计树。

把包当成不可信输入，是因为下一个模型会把包里的句子当成新的系统指示。交出方的「完整」、字节级的结构检查、以及换模型之后语义有没有接上，是三件不同的事。混在一起时，一份能打开的文件就会被说成另一个模型已经理解了工作。

## 5. 对照本库

本库的跨次记录在 `dev-process-handoff`。开工仍是 `demo-kickoff-card`。完成仍是 `dev-review-verify` 的当次产物。

### 可借鉴

- `dev-process-handoff` 继续写下当前目标、停在哪、下一句能执行的动作、完成标准、仍有效的决定、约束、被否决和失败过的路径、已经回答的问题，以及哪些外部事实要重查。
- 旧交接不带来新的提交、发布或改正式页面的权限。`drission-crawler` 的登录、验证码和提交仍交给使用人。
- 材料上有缺口就写明。`work-doc-writer` 里未知事实保持待确认，不写成已决定。
- `dev-review-verify` 不把一份可读的交接当成 LIVE。笔记结构不能代替打开的页面、导出的文件或启动的窗口。

### 不要照搬

- 不把 `dev-process-handoff` 换成三层协议、压缩包、审计包、哈希或评分卡。
- 不加入交出和接收脚本，也不在本库宣称跨模型连续性。来源 README 自己把这一点标成证据未齐。
- 不为了省事把整个工作区打进包。
- 不把交接写成第二张开工卡。`demo-kickoff-card` 仍只管一次 DEMO 进场。

## 6. 一句话建议

交接写清停在哪、下一步一句，以及哪些路不要再走；历史记录不带来新的提交权限。本库继续用现有交接，不换协议包。
