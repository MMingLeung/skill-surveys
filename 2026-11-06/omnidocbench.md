## 2. 它是什么

这是文档解析和 OCR 的评测基准，不是又一个解析器。技能帮助把一次评测跑完并读懂结果：核对真值与预测路径，尽量用容器跑，再从结果目录里取出分数和会影响分数可信度的计数。

评测把整页 Markdown 对上标注。综合分由文本、表格和公式三块合成。中文 README 写了榜单和各模型分数。本笔记不把这些数字当成当日复测，也不转抄技能报告样例里填好的分数。

## 3. 写法特点

- description 把触发收在评测、部署、排错和读结果上。简单问题可以短答。用户给了路径，才生成针对那次路径的做法。
- 开跑前只追问会改变命令的缺口：用容器、本机环境还是远程，要不要公式指标，真值文件、预测目录和输出目录在哪。
- 长任务开始前先核对文件在不在、预测是不是页级 Markdown、有没有空文件。空文件不一定让任务失败，但要写进报告，因为空预测会把分数拉低。预测数为零，多半是把父目录当成了真正的 `markdown/` 目录。Linux 上真值文件名大小写不同，先在旁边找，再判断数据缺失。
- 结果不只报一个综合分。要同时看指标文件、运行摘要、阶段执行和运行环境。阶段里公式和表格的超时、错误、异常为零，才算干净的一轮。匹配超时是警告，不自动判失败。
- 输入用只读方式挂上。输出用带时间的新目录，不覆盖、不删除已有结果。远程断开后要能找回这次输出在哪。
- 很长的拉取或评测，除非使用人明确说要跑，否则先问。后台跑的时候告诉对方任务和输出路径，跑完再解析。
- 没有容器、或要改评测代码时，才走本机环境，并先检查公式渲染依赖。技能把容器写成默认，因为公式指标依赖一串排版工具，本机很容易缺。

## 4. 原理与设计意图

作者默认使用者会把「命令退出了」说成「这篇文档已经解析对了」。所以完成条件是结果文件加上校验计数，不是对话里的一句分数。

全量和子集也不是同一件事。配置可以按页属性筛选。页数对不上、空文件、超时，都会让榜单上的数字和这一次不可比。技能因此要求把这些计数和分数放在同一份报告里。

它解决的是「怎么公平地比解析器」，不是「把这一份公文或发票读成可交付的 Word」。

## 5. 对照本库

本库的文档技能负责文种、版式和当次读到的范围。这份仓库对得上的是：空结果要写明，分数或成功退出旁边要有当次证据。

### 可借鉴

- `work-doc-writer` 继续把扫描件的空文本写成没识别到文字，并写上页范围。预测目录是空的、或只有一部分页有字，不能写成整份已经读完。
- `dev-review-verify` 若某次检查给出分数、覆盖或通过，旁边留下当次输出路径，以及超时、错误、空文件这类会改变结论的计数。退出码成功仍要读那份输出。
- `word-thesis-format` 的完成仍是打开后的预览。评测综合分不代替版式是否可用。

### 不要照搬

- 不把 OmniDocBench 的容器、评测配置或榜单接进 `work-doc-writer`、`word-thesis-format`。不替换现有的 PaddleOCR 发票路径。
- 不把科研用数据集或会离开本机的解析，当成内部公文和发票的默认识别。涉密和内网材料留在现有本机路径。
- 不把 README 或技能样例里的分数写进收工标准。本笔记不把这些数字当成当日复测。

## 6. 一句话建议

解析是否可信，看当次结果文件和空页、超时这些计数；本库继续用现有识别和打开后的页面验收，不把这份评测基准换成发票或公文引擎。
