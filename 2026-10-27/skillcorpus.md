## 2. 它是什么

SkillCorpus 把散落在公开仓库里的 `SKILL.md` 收成可检索的语料：聚合来源，过安全和许可门，做质量与去重，再在代理回答前放入少数和任务相关的技能。插件接到多个代理宿主。

检索有两种模式，说明写明互斥：默认把检索做成工具，由代理在需要的那一步调用；另一种是每一轮回答前自动注入。选择结果是 0 到 2 条，不是把命中的全塞进去。索引默认只用名字和 description。正文被当成停用词噪声，需要时才能改回索引正文。

评测包和主安装分开，里面是三套基准。另有退役逻辑：看某个模型不带这段技能时已经做得怎样，而不是只看「加上技能提高了多少」。

## 3. 写法特点

- 插件文档把 description 定义成搜索面。正面例子写任务、输入，以及使用人会说的那几句；反面例子是只有「PDF 助手」这类主题词。没有 description 的技能只能靠名字被找到。
- 许可是三档，默认排除。宽松许可进入语料；copyleft、非商业、以及需要逐条看的共享许可默认不进。解析不了、缺失、自定义的条款一律不当成可收录。技能先是未激活，只有许可审计才把来源打开。导出行带上来源地址和许可名。作者可以要求下一次发布整源移除。
- 质量在 README 里分成效用、稳健、安全三个维度。策展代码把一类安全问题设成硬门槛，命中则分数归零；过短和过长的正文降权。没有模型接口时，分类和打分退回规则，流水线仍然跑完，而不是跳过这道门。具体权重和旗标表属于实现，本笔记不抄。
- 评测比较的是同一套运行环境、带上语料和不带语料。README 对论文表格的解读是：任务依赖模型自己没有的过程步骤时，提升更明显；模型本来就能做的开放任务，提升较小。这些是作者引用的论文数字，不是当日复跑。
- 退役按「不带技能的水平」而不是按增益。模型已经会做的步骤，留在语料里会占用检索。
- 安装剧本有一节完成定义，按宿主分别写怎样算装好。本笔记不转写安装步骤。

## 4. 原理与设计意图

技能一多，description 会互相挡住。先做许可和安全门，再只放进 0 到 2 条，是为了不要安装整个市场。只索引名字和描述，是因为正文里的套话会把不相关的技能召上来。门偏严，宁可不选，也不选错。这和「顶层技能太多就会叫错」是同一问题，发生在检索端。

许可默认排除，是因为产品要再分发别人的技能正文。评测把「换了一个代理」和「多读了一段技能」分开。退役则防止语料只增不减，把模型已经内化的步骤继续注入。

## 5. 对照本库

本库是固定的几份交付 SOP，没有技能市场，也不再分发外部 `SKILL.md`。

### 可借鉴

- `evals.json` 继续只判断该不该触发。SkillCorpus 多提醒一层：带上技能之后，差的应是模型容易跳过的过程，而不是它本来就会写的文章。`dev-review-verify` 已经把「会不会叫错」和「真实产物」分开。以后若给开工卡或工作文档加产物检查，只加四块是否齐全、按钮名是否回读自源码这类本库自己的断言。
- description 写使用人会说的话。`demo-kickoff-card`、`drission-crawler` 已有触发词。自查时看 description 是否只剩技能主题，那种写法在这里被当成搜不到。
- 新技能仍先问会不会挡住已有 description。这里的做法是一次只留 0 到 2 条。本库不建检索器，用在「要不要新增顶层名字」上。
- 许可或来源说不清的外部正文不收进可复用技能。只记结构和意图。这和专有文档技能只作对照是同一条。
- 八个现有技能对应的是交付里会跳过的门：开工确认、浏览器停手、启动就绪、政务文案、文档模板、收工证据、交接。模型不看技能也会做的泛泛写作，不必再拆成新技能。

### 不要照搬

- 不把 SkillHub、检索模型、策展流水线或安全扫描装进本库。
- 不按效用、稳健、安全三维给本库技能打分，也不把旗标表写进 `dev-review-verify`。
- 不在每一轮自动注入其他技能。本库技能由任务路由。
- 不把 `INSTALL.agent.md` 的安装步骤写进任何技能。
- 不把论文里的通过率变化写进本库验收标准。

## 6. 一句话建议

技能要被选中，靠触发句和许可写清楚；评测看带上它之后过程性任务有没有变。本库不建语料库，只保持少量交付技能和现有触发样本。
