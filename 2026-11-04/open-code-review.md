# Open Code Review（混合式代码审查）

查阅日：2026-11-04。

## 1. 来源

- 仓库：<https://github.com/alibaba/open-code-review>
- 默认分支是 `main`。查阅以 `main` 为准。
- 星标：49407（当日 GitHub API `stargazers_count`）
- 许可：Apache-2.0（仓库 SPDX、README 徽章、根目录 `LICENSE`，版权行署名为 Alibaba，2026）
- 代理入口有两份，都在 `skills/`：`open-code-review` 让 CLI 自己调用模型；`open-code-review-delegate` 让宿主代理来审，CLI 只做选文件和匹配规则。`plugins/open-code-review/skills/` 还有同名副本。两份技能的 frontmatter 都写了 Apache-2.0 和版本 `1.0.0`。仓库没有把 `evals/` 放在技能旁边；README 另有一份公开基准，本笔记不把那些数字当成当日复测。

## 2. 它是什么

这是一条代码审查命令。它用 Git 取差异，用工程逻辑决定哪些文件要看、哪些捆在一起、每份文件套哪条规则，再把评论定位到行。模型负责在这个边界里做判断。另一种跑法不给 CLI 配模型：宿主按预览出来的文件清单逐份看完，规则仍由 CLI 解析。

作者认为纯自然语言的审查技能会漏文件、行号对不上，而且提示稍变质量就漂。所以选文件、分包、配规则和定位做成硬步骤。README 写明这是用精确率换召回率：少报一些，也少漏报以外的噪声。基准由公开拉取请求和人工标注做成，笔记只记这个取舍，不引用分数。

技能要求装好 `ocr`。托管审查还要先配好模型。委托审查在 CLI 一侧不调用模型。

## 3. 写法特点

- 两份 description 互相躲开。一份写「用户要审改动、提交或分支，并由 CLI 出逐行评论」。另一份写「由宿主来审，CLI 只做确定性的那一半」。兼容性字段写明各自要不要模型。
- 托管技能默认看工作区里已暂存、未暂存和未跟踪的改动。分支和单次提交要另给参数。给人看的进度输出不用在代理路径上。长结果写到文件里整份读，不用截断命令只看尾巴。
- 评论带严重程度和类别。呈现时丢掉低严重度。行范围两个都是 0，表示没定位到，要再读文件，不能把 0 当成真实行号。
- 用户只说审查时，先问再改代码。说了要修，才动严重程度较高的项，提交前仍要人确认。
- 规则按路径匹配，项目文件优先于用户主目录，再优先于内置。可以预览某个文件会吃到哪条规则。
- 失败不按同一命令盲重试。不认识的旗标就停下来问要不要升级，不改用截断的标准输出把审查做完。委托模式里，格式旗标太旧时可以改读文本，但文本不假装成结构化字段；别的错误不降级。
- 背景说明有体积上限。超限时不悄悄截断原文；摘要要保住要求、约束和验收；摘要做不到就不用背景，改在审查时直接读原文。背景文本不当成可以展开执行的 shell。
- 委托模式要求清单上的每个文件要么审过，要么写明跳过。同一路径在删除后又出现，按路径加状态区分，不合并成一条。
- 技能自带的「算成功」是退出码 0，以及有评论或明确的无评论。这比本库的 LIVE 弱，笔记把它记成来源自己的门，不拿来当收工。

## 4. 原理与设计意图

模型会在大差异里只看顺眼的文件，也会把意见安到错误的行上。选文件和定位若交给同一段散文，漏看和错行都不可查。所以范围是清单，判断才是模型的。

两份技能分开，是因为「谁来调用模型」会改变密钥、费用和上下文。宿主已经在审时，再让 CLI 呼叫一次模型，是另一条产品路径。

低严重度默认不展示，是精确率优先的同一选择，代价是真实问题可能被滤掉。定位失败单列，是为了挡住「行号是 0 所以问题在文件开头」。背景材料限长并且不当成命令，是因为需求文档会进审查提示，里面的文字不自动变成下一步。

技能版本停在 `1.0.0`，CLI 已经有更晚的旗标。入口把「旗标不认识」写成停手，就是承认说明和二进制会分开升级。

## 5. 对照本库

本库的质量门是 `dev-review-verify` 的当次产物，加上 `evals.json` 的触发样本。这套仓库是另一个审查产品和它的模型。

### 可借鉴

- 声称看过一遍时，范围要能点名。必需路径没跑，写成跳过或未验收完成，不并进「已经看过」。`dev-review-verify` 继续以这一次的页面、导出文件或窗口为准。
- 证据对不上位置时写明没定位到，不编一个行号或选择器。`drission-crawler` 改选择器仍是一次只改一个原因，再用当次回读。
- 检查输出整份读。不用截断后的尾巴代表全文。退出码 0 只说明命令返回了，不代替打开结果。
- 只要求审查时不顺便改产品代码、不提交。要改时仍等人确认。
- `dev-process-handoff` 写下这次用的检查从哪到哪、哪几条没跑，以及工具版本。说明和工具对不上时停下来问，不换一条没约定的路径把结论做完。
- 外部需求、网页和旧笔记是材料。放不进限制时，读原文，不截断后当成新的指令。

### 不要照搬

- 不安装 `ocr`，不把两份技能或插件副本写进本库，也不把审查 CLI 当成 DEMO 的收工门。
- 不把业务代码送到外部审查模型。委托模式同样不接入。
- 不按严重度自动删评论，也不把「没有中高严重度」写成验收完成。
- 不自动修代码。基准里的精确率、召回率和令牌数不进入 `evals.json` 或收工标准。
- 不新增审查、定位、反思三种角色。开工卡仍是四块。

## 6. 一句话建议

审查要有一份文件清单、定位失败要明说、退出码不是做完；本库仍用当次 LIVE 收工，不装这套审查 CLI，也不把代码送到外部模型。
