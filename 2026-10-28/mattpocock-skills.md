## 2. 它是什么

作者放在自己代理目录里、每天用来做工程的一组小技能。README 写明这些技能要小、可改、可组合，并点名 GSD、BMAD、Spec-Kit 一类会把整条流程收走、出了问题也不好改。本库对照时主要看开工前问清、规格、测试、审查、拉取请求正文、交接和复盘。其余如术语表、工单分诊、大型路线图，属于通用软件工程。

技能分成两类：只有人点名才运行的，负责编排；人和模型都可以按任务捡起的，只放可复用纪律。人点名的技能可以去调用后者，不互相调用。

## 3. 写法特点

- 多数 description 用 “Use when …” 写时机。交接、写成规格、复盘等编排技能标了禁止模型自行调用。
- `tdd` 正文短，细则指向旁边的测试和替身说明。规则是：先和人说好测哪些公开边界，再写会失败的测试，然后只写刚好通过的实现。一次只做一条。测试看外部行为。重构不塞进这一轮，留到审查。
- `to-spec` 不重新采访，只把已经谈过的内容收成规格，并先核对测试边界。规格里写问题、做法、用户故事、实现决定、测试决定和范围外。实现决定不写具体文件路径和代码，避免很快过时。
- `code-review` 从固定起点看差异，分两轴并行：符不符合仓库成文规范，符不符合原来的规格。两份报告并列，不合并排序。没有规格就写没有规格，不编一条通过。
- `pr` 的正文固定三块：最小能看懂改动的摘要、改前与改后的证据、合并风险（能否撤回、影响面）。
- `handoff` 把当前对话压成给下一个代理的文档，放在系统临时目录，不放进仓库。已经落在规格、计划、提交和差异里的内容用路径指过去，不重写。文档里点名下一步该用哪些技能。密钥和个人信息去掉。同目录下另有一份进行中的变体，写完摘要后立刻拉起下一个后台代理。那是宿主能力，不是本库的交接。
- `retro` 复盘的是代理的环境：不好找文件、缺自动检查、规范没拦住、入口文件太长、工具太贵、写了也不起作用的句子。机械规则优先做成检查，只有判断才留在文字规范里。审查方负责规范，实现方上下文更挤，不把长规范堆给实现方。

## 4. 原理与设计意图

仓库假设模型会做错事：没对齐就做、说得太长、没有反馈仍继续写、改得快所以结构更快变烂。对应的办法是先问清、共享用词、在说好的边界上测试、分开审查标准和规格。

两轴分开，是因为「写得合乎习惯」和「做的是约定的那件事」会互相掩盖。交接放在临时目录并指向已有文件，是为了避免第二份会过期的说明书，也避免把密钥写进仓库。

复盘去改环境和检查，是因为同一类错误再用一段提示去挡，不如一条会失败的检查。

## 5. 对照本库

本库已有开工卡、收工核对和交接。这组技能里能对上的是问清、证据和交接时不另写一套事实。

### 可借鉴

- `dev-process-handoff` 继续写行为、默认值和验收变化，并指向这次的证据路径。对话里已经写过的内容不重抄。密钥和现场数据不写进交接。
- `dev-review-verify` 把两件事分开写：有没有遵守本库已有的收工程序，有没有当次打开的产物。一边过了不能代替另一边。没有约定的核对项就写没有，不补一条看起来完成的结论。
- `demo-kickoff-card` 保持一轮问完。问清发生在开做前；交接不再重新采访。
- 能用检查脚本抓住的问题，继续放在脚本和 LIVE 里。`retro` 里「机械规则做成检查」和这条同向。

### 不要照搬

- 不把这组技能装进本库，也不新增术语表、架构决策记录、工单状态机或路线图技能。
- 不把交接写成系统临时目录里的会话压缩，也不在交接后自动拉起另一个代理。
- 不把红绿重构、公开边界确认和代码气味对照写进 `drission-crawler` 或 `windows-gui-bat-launcher`。
- 不把拉取请求模板的三块替换本库交接。合并风险不是驻企验收的完成条件。
- `government-service-design` 不增加方案竞选或代码审查轴。

## 6. 一句话建议

只吸收「交接指向已有证据、审查两轴不合成一个结论」；整套工程技能和临时交接文件不进入本库。
