- 默认分支是 `main`。查阅以 `main` 为准。
- 星标：53444（当日 GitHub API `stargazers_count`）
- 许可：MIT（仓库 SPDX 与 `LICENSE`）
- 执行入口是 `skills/security-audit/SKILL.md`。旁边有分阶段说明、`report-schema.json`，以及不依赖第三方包的两份校验脚本：发现记录一份，覆盖账本一份。攻击面分册只作路由，本笔记不摘那些分册，也不写利用步骤。

## 2. 它是什么

这是给编码代理的安全审计技能。加载之后默认只提供指导。使用人明确要求审计代码库、做完整审查，或要一份报告时，才走完整流程。两种意思都说得通时，先问一个问题，再建文件。

完整流程在公开说明里是六段：摸清边界和已有证据，按覆盖账本分派检查，逐条验证候选，写成结构化记录，换一双眼睛核对最终记录，再生成不含目标细节的报告。本笔记只取证据门禁这一层。

## 3. 写法特点

- 技能开头写明：加载不等于授权跑完全程，也不等于可以建文件。指导模式只用相关的几段。完整模式才按顺序走完。
- 每条候选要写清较低信任的一方、接受的输入、本来的控制、越过的边界、受影响的对象，以及具体结果。对不上这几项的，不升成已确认问题。
- 优先级和把握分开写。严重度看可能性和影响，不看「偏离了检查清单」。清单差异、没有可到达边界的加固建议，被写成反例。
- 发现的人和验证的人不是同一个。验证者按源码重新看，不沿用发现者的叙述。
- 记录是机器可读的。模式至少分成三种结局：已经独立演示的问题、源码上站得住但验证被卡住的待验证、验证后被否定的候选。待验证必须留下卡住的事实。被否定的要留下理由。已确认的记录带文件与行号上的证据、严重度拆分和置信理由。
- 只有散文、无法去重、也无法再核的结果，被写成反例。同一来源上已经确认过的记录不拿来当下一轮的样板。
- 校验脚本对照模式检查记录和覆盖账本。脚本负责格式和约定，不代替源码里的那次核对。
- 看不到的部署、代理和身份策略，不猜。证据停在本机能看到的源码和受控检查。修法写最小的一处源码改动。

## 4. 原理与设计意图

模型容易把风格问题写成漏洞，也容易自己发现、自己宣布已经证实。作者把「说了」和「另一轮核对过」拆开，并把结局收成可校验的记录。

覆盖账本是为了看见哪些面查过、哪些面没有。待验证不是失败，也不是通过，它表示还缺一个事实。完整流程默认不启动，是为了避免一句含糊的安全问题就铺开审计文件。

## 5. 对照本库

本库不做漏洞审计。对得上的是收工证据：声称完成之前，要有当次、可再读的结果，并且发现和复核不要合成一句「已通过」。

### 可借鉴

- `dev-review-verify` 维持两层：`evals.json` 看会不会叫错技能，LIVE 看当次产物。检查脚本成功退出仍要读输出。必需路径有一条失败，整次不写验收完成。跳过要写原因。
- 技能被选中不等于跑完全程。description 继续写清何时做收工核对、何时只改文档或界面。意思含糊时先问，不先铺验收文件。
- `dev-process-handoff` 只记录这次变了的行为、默认值和验收口径。没有当次证据的「应该没问题」不写进交接。

### 不要照搬

- 不把审计阶段、覆盖账本、发现模式或校验脚本写进 `dev-review-verify`。交付收工不使用严重度等级。
- 不把攻击面分册、狩猎步骤或利用记录摘进本库任何技能。
- 不增加「独立子代理复核」作为收工的必经步骤。本库的复核是使用人看得到的页面、文件或窗口。
- 不把待验证状态引进开工卡。缺证据时结论写成未验收完成，并写缺的是哪一项。

## 6. 一句话建议

问题要能被另一轮核对，记录要能被校验；本库收工仍看当次产物和 LIVE，不把安全审计流程写进交付技能。
